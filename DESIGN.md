# Architectural Design & Technical Decisions

## 1. Механизм отмены устаревших запросов

### Почему выбрана реальная отмена через `AbortController`, а не флаг актуальности или timestamp

Подход с флагом (`isCurrent`) или сравнением меток времени (`timestamp`) решает проблему только на уровне отображения (UI), но оставляет проблему на сетевом и системном уровнях:

- Браузер продолжает держать открытым TCP/TLS-соединение и расходовать сетевой трафик на скачивание тела устаревшего ответа.
- Движок продолжает тратить ресурсы CPU и памяти на парсинг ненужного JSON (`response.json()`).
- При медленном соединении (например, Slow 3G) несколько «висящих» параллельных запросов конкурируют за полосу пропускания, замедляя загрузку действительно актуального запроса.

В проекте используется `AbortController` (`src/controller/searchController.ts`, метод `handleInput`):

1. **Немедленная отмена при каждом изменении ввода:** Как только пользователь вводит новый символ или очищает поле, вызывается `this.currentAbortController?.abort()` — ещё до истечения таймера `debounce`. Это гарантирует, что любой запрос, уже ушедший в сеть, прерывается на уровне сетевого стека браузера (в DevTools Network такие запросы получают статус `canceled`).
2. **Композиция сигналов отмены и таймаута:** В методе `executeSearch` пользовательский сигнал объединяется с сигналом таймаута с помощью `AbortSignal.any([abortController.signal, AbortSignal.timeout(this.timeoutMs)])`.
3. **Разделение сценариев в `catch`:** Функция `classifySearchError` (`src/api/classifySearchError.ts`) различает типы исключений:
   - `AbortError` (отмена самим приложением при новом вводе) классифицируется как `{ type: "Aborted" }` и тихо игнорируется, не показывая пользователю ложную ошибку.
   - `TimeoutError` (превышение `8000 мс`), `HttpError` (статусы 5xx и прочие неуспешные, кроме 404) и сетевые сбои (`TypeError`) переводят интерфейс в состояние `error` с возможностью повторить последний запрос.
   - Статус `404` обрабатывается в `searchCountries` (`src/api/countriesApi.ts`) как штатный пустой результат (`[]`), а не исключение.

## 2. Обоснование выбранной задержки `debounce` (300 мс)

В `SearchController` выбрана задержка **300 мс** (`delay = 300`).

- **Что будет, если убрать задержку (`0 мс`):** При вводе слова из 10 букв (например, `"Madagascar"`) приложение отправит 10 сетевых запросов подряд, 9 из которых будут мгновенно отменены. Это создаёт лишнюю нагрузку на API, трафик и вызывает визуальное мерцание индикатора загрузки при каждом нажатии клавиши.
- **Что будет, если сильно увеличить задержку (`1000+ мс`):** Интерфейс начнёт восприниматься как медленный и «зависший» — пользователь уже закончил печатать, но секунду или дольше не видит никакой реакции.
- **Почему `300 мс` оптимально:** При средней скорости печати (~200–300 знаков в минуту, то есть ~1 символ каждые 200–250 мс) пауза в `300 мс` позволяет объединить серию быстрых нажатий в один сетевой запрос и при этом ощущается пользователем как мгновенный отклик после завершения ввода.

## 3. Асимптотическая сложность (Big O)

### Функция `mapCountryResponse(raw)` (`src/models/mapCountryResponse.ts`)

- **Временная сложность (Time Complexity):** **$O(L + C + B)$** для одной страны, где:
  - $L$ — длина массива `raw.languages` (проход через `.map()`),
  - $C$ — длина массива `raw.currencies` (проход через `.map()`),
  - $B$ — длина массива `raw.borders` (поверхностное копирование `[...raw.borders]`).
  
  Поскольку для любого существующего государства количество официальных языков, валют и сухопутных границ ограничено небольшой константой (обычно от $0$ до $15$), на практике преобразование одной записи выполняется за амортизированное константное время **$O(1)$**. Для всего списка из $N$ найденных стран общая сложность составляет **$O(N)$**.

- **Пространственная сложность (Space Complexity):** **$O(L + C + B)$** на одну страну (создаются новые массивы `borders`, `languages`, `currencies` без мутации исходного объекта API) и **$O(N)$** для результирующего массива карточек.

## 4. Применённые принципы чистого кода

1. **Single Responsibility Principle (Принцип единственной ответственности):**
   - `src/api/countriesApi.ts` (`searchCountries`, `HttpError`) — отвечает исключительно за HTTP-запрос и проверку статуса ответа.
   - `src/api/classifySearchError.ts` (`classifySearchError`) — отвечает только за классификацию перехваченных ошибок.
   - `src/models/mapCountryResponse.ts` (`mapCountryResponse`) — отвечает только за нормализацию сырых данных API в модель приложения `Country`.
   - `src/utils/debounce.ts` (`debounce`) — отвечает только за отложенный вызов функции с возможностью отмены таймера (`.cancel()`).
   - `src/controller/searchController.ts` (`SearchController`) — управляет состоянием поиска и жизненным циклом `AbortController`, не зная о DOM.
   - `src/view/appView.ts` (`AppView`) — отвечает исключительно за отрисовку DOM и обработку пользовательских событий.

2. **Decoupling / Separation of Concerns (Независимость логики от UI):**
   - `SearchController` не импортирует `AppView` и не обращается к `document` или `window`. Взаимодействие с представлением построено через колбэк `onStateChange: (state: SearchState) => void`, благодаря чему вся асинхронная логика и гонка запросов покрыты быстрыми модульными тестами без браузера.

3. **Pure Functions & Immutability (Чистые функции и иммутабельность):**
   - `mapCountryResponse` и `classifySearchError` являются чистыми функциями без побочных эффектов: при одинаковых входных данных они всегда возвращают одинаковый результат и не мутируют переданные аргументы (например, `borders` копируется через `[...raw.borders]`).

4. **Security by Design (Защита от XSS):**
   - В `src/view/appView.ts` весь динамический интерфейс создаётся через `document.createElement`, `replaceChildren` и свойство `textContent`. Использование `innerHTML` и `insertAdjacentHTML` полностью исключено.
